# DataTrace 全面工程质量审查（2026-10-11）

审查基线：`eca62c9a6c4b9497feead894e5c801d963de1994`。审查开始时工作区干净。本轮交付审查报告和验证产物，不修改业务实现。

**结论：项目有较扎实的工程基础，但整体尚不能按 L3「现场可靠」验收。** 分层、自动化测试、诊断、补传、MES Outbox 和备份已有实现；阻碍验收的主要问题是采集幂等、断电一致性、配方冻结、授权撤销和恢复边界。具备 L2 的基础能力，部分能力达到 L3/L4；未完成长稳和真机验证，不能据此认定整个系统已稳定达到 L2，更不能用测试数量直接宣称 L4。

项目真实职责是 .NET 8 Blazor Server 的 PLC 产线采集与数据追溯，含曲线判定和文件源采集；当前未见视觉工作流编辑器、相机适配器或机器人动作调度。用户提出的质量原则适用，相关设备安全能力按真实 PLC 读写范围评估，不把不存在的功能计为缺陷。

- 重跑核心测试与组件测试，执行完整浏览器回归；另外直接调用本轮编译产物做边界探针。
- 「静态确认」表示代码已具备触发问题的条件，不代表已在客户真机观察到故障；「探针复现」表示直接执行对应实现得到问题结果。
- 未进行真实 PLC/现场联机、断电注入、磁盘写满、72 小时长稳、生产规模容量测试、实际升级/恢复演练或渗透测试。没有执行任何生产数据恢复或设备写入。

## 3. 具体问题（按严重度）

### R01 · P1 · 回写失败后，同一 PLC 触发可被重新采集

**静态确认。** [触发调度](D:/code/DataTrace/src/DataTrace.Collector/CollectionHostedService.cs:504) 只用 `_busy` 防止执行中的并发，任务退出即移除；下一轮仍按寄存器等于 TriggerValue 判断触发。[回写失败](D:/code/DataTrace/src/DataTrace.Collector/StationCollectPipeline.cs:102) 只改变显示状态，没有锁存「已采集、待确认」事件。若记录已提交而所有回写均未成功，寄存器仍为 1，下轮会再次采集；首站会把旧会话标异常并产生新流水号，其他站也可新增重复记录。重启后同样没有持久化触发确认记录。MES 幂等键对应新生成意图，无法消除此类业务重复。

**修复方向：** 为 PLC 事件建立设备事件号或握手序号，以及持久化的采集/提交/确认状态。提交之后只重试确认；无法确认时进入明确的阻塞状态，核对设备后才能恢复。采集业务效果使用唯一幂等约束。

**验收：** 在读后、提交后、回写前/中各杀进程或断链，同一设备事件只产生一次业务采集和一次 MES 意图；新事件可继续；恢复依据 PLC 实态，不能仅凭旧 UI 状态。

### R02 · P1 · 月库提交与配置库在制索引之间仍有硬退出窗口

**静态确认。** [RuntimeStore](D:/code/DataTrace/src/DataTrace.Infrastructure/Persistence/RuntimeStore.cs:148) 先提交月库，再更新 config.db 的 ActiveSessions。普通异常由 `PostCommitStateUpdateException` 和 spool 修复，这是已有优点；但提交成功后、索引写入前直接断电/终止进程不会进入 catch，也不会生成补偿文件。首站记录已存在、索引却缺失；末站已经关闭、索引仍在。当前启动链未见针对该窗口的全局重建/对账机制。按托盘更新索引也缺少业务上的逐托盘序列化边界。

**修复方向：** 仿照 MES 意图，在月库同事务写入在制状态更新意图，幂等转运；启动对账不完整意图并核对 open/closed 会话。按托盘/会话串行变更或带条件版本更新，避免旧事件覆盖新事件。

**验收：** 精确在两个提交间杀进程；重启后索引与月库一致，无新建 ORPHAN、无恢复旧会话覆盖新会话。

### R03 · P1 · 在线全量备份只验证单文件完整性，未保证业务一致性

**静态确认。** [备份主流程](D:/code/DataTrace/src/DataTrace.Infrastructure/Backup/DatabaseBackupService.cs:133) 枚举数据库，先逐库 SQLite Backup，再复制曲线/归档/spool。`_gate` 仅防两个备份并行，未冻结采集、补传、MES relay 和保留任务。config.db 在 T1、月库在 T2：两者期间完成一次首站或末站会使恢复后的索引与记录不一致。跨月创建的新月库也可能不在最初枚举列表；备份月库后保留任务删除曲线，会造成记录引用的文件缺失。SHA256/quick_check 均通过也不能证明这组数据可恢复成同一个业务时刻。

**修复方向：** 先实现可验收的停写快照：暂停新触发、等待在途任务并协调补传/保留/MES 后捕获；长期方案采用版本化快照与一致性水位。发布 complete 前检查 DB 引用的曲线/归档、ActiveSessions 及未完成意图。

**验收：** 持续采集、补传、跨月与保留清理时备份，再在隔离目录恢复，校验引用存在、索引一致、MES 不丢不重复业务投递。分别说明备份时刻、RPO 与 RTO。

### R04 · P1 · 「冻结配方」实际只冻结编码，没有冻结版本与限值

**部分探针复现。** [SessionRecipe](D:/code/DataTrace/src/DataTrace.Collector/SessionRecipe.cs:12) 使用当前配置按 frozenCode 查找 Recipe。修改同一型号的限值会影响已有在制件；改名后旧码找不到（探针返回 null），停用或删除同样可能回落到默认点位限值。[Resolver](D:/code/DataTrace/src/DataTrace.Domain/Evaluation/RecipeLimitResolver.cs:19) 对 null/停用型号使用默认值。另有 [读取在制型号失败](D:/code/DataTrace/src/DataTrace.Collector/StationCollectPipeline.cs:247) 时静默采用当前型号的降级路径。记录仍可能保留旧型号码，实际判定规则却已不同。

**修复方向：** 会话冻结不可变 RecipeRevision/参数快照；记录包含配置版本、算法/曲线基线版本或指纹。旧版本保留至所有引用结束；版本不可用时阻止判定并给出可恢复故障，不静默换规则。

**验收：** 在制期间改限值、改名、删除、停用、切换型号和模拟索引读取异常，旧件使用同一冻结规则，新件使用新规则，记录能重建当时判定。

### R05 · P1 · 两个孤儿托盘同秒触发，会生成相同唯一流水号

**静态确认。** [孤儿路径](D:/code/DataTrace/src/DataTrace.Collector/CollectSessionCoordinator.cs:95) 使用 `ORPHAN-yyyyMMddHHmmss`，没有工站、托盘或唯一随机部分。[月库](D:/code/DataTrace/src/DataTrace.Infrastructure/Persistence/RuntimeDbContext.cs:24) 对 PalletSession.SerialNo 有唯一索引。两个不同孤儿托盘同秒触发时第二条无法落库；补传仍保留相同流水号，冲突不会随重试消失，并可能阻塞随后有效缓存。

**修复方向：** 孤儿事件也使用可靠唯一 ID/统一流水生成器；保留 ORPHAN 作为状态或前缀；对确定性冲突提供诊断与隔离，避免只做无限重试。

**验收：** 多工站同秒至少两个不同孤儿托盘都成功保留异常记录，重启补传不撞号，后续正常件继续。

### R06 · P1 · 长连接用户撤权或删除后，已打开页面缺少重新授权

**静态确认；真实双浏览器撤权流程尚未复现。** [服务注册](D:/code/DataTrace/src/DataTrace.Web/Program.cs:137) 使用默认交互式认证状态，未注册周期性/事件驱动的 Identity 重验证 provider；[角色修改](D:/code/DataTrace/src/DataTrace.Infrastructure/Identity/UserAdministration.cs:147) 未见配套电路失效机制。[工站保存](D:/code/DataTrace/src/DataTrace.Web/Components/Pages/Stations.razor:1369) 依赖页面入口的 Authorize，写服务不在动作时重新查询当前操作者权限。Blazor 电路持续使用先前主体，Cookie 校验不能自动覆盖已有电路的每次事件。撤掉 Engineer/Administrator 或删除账号后，旧页面仍可能执行敏感配置操作。

**修复方向：** 对配置、用户、恢复、仿真写等命令实施动作时授权，使用可信当前用户及数据库权限；角色/账号变化主动失效相关电路/会话，配置重验证周期。密码重置也验证既有电路失效。

**验收：** A 浏览器打开敏感页，B 管理员撤权/删号，A 不刷新继续保存必须拒绝并留失败审计。参考 [微软 Blazor 认证文档](https://learn.microsoft.com/en-us/aspnet/core/blazor/security/?view=aspnetcore-8.0)。

### R07 · P1 · 停机先释放 PLC 队列，未等待在途采集任务

**静态确认。** [StopAsync](D:/code/DataTrace/src/DataTrace.Collector/CollectionHostedService.cs:613) 先 Dispose 队列，最后才调用 base.StopAsync 取消采集循环；采集通过不保存 Task 的 `Task.Run` 执行，停机没有 join/drain 在途任务。队列关闭与扫描/保存/回写并发，可能导致库已提交但确认/索引步骤未完成，宿主已继续退出。队列处理循环取消时也未逐个完成所有待执行请求的 TCS；没有独立取消令牌的调用方可能长期等待。回写 finally 的 Delay 使用已取消令牌时可抛出，跳过最后的状态/事件/锚点日志。

**修复方向：** 停止接收新事件 → 取消扫描并等待退出 → 在限时内汇合在途任务并持久化未完成状态 → 释放队列/驱动。关闭队列时为待处理请求明确设置取消/失败。

**验收：** 高负荷中反复停/启与服务升级，停机时间受控，无悬挂 Task，已提交件可恢复确认，未提交件有恢复记录。

### R08 · P1 · 升级备份与数据回滚不支持外置 DataRoot

**静态确认。** 应用明确支持绝对/外置 DataRoot，但 [Backup-DtUpgrade](D:/code/DataTrace/deploy/_common.ps1:334) 固定备份 InstallDir/data，[rollback -RestoreData](D:/code/DataTrace/deploy/rollback.ps1:122) 也固定恢复该目录。当实际库在 E:/CustomerData 时，升级快照未包含实际数据，回滚并没有恢复真正升级过的库。新 `restore.ps1` 的 DataRoot 处理不能自动修复这条独立的 upgrade/rollback 路径。

**修复方向：** 两套路径共用 DataRoot 解析和完整备份格式；记录原实际根路径，验证备份/恢复对象与运行配置一致。先完成发布包与备份校验再停机；确认进程已停后再交换数据和二进制。

**验收：** 安装目录与数据目录位于不同磁盘，运行 upgrade → 故障 → rollback -RestoreData，验证真正数据目录、schema、业务记录及服务运行方式恢复到预期。

### R09 · P1 · 驱动把成功但长度不足的 PLC 响应补零

**探针复现。** [ToWords](D:/code/DataTrace/src/DataTrace.Plc.Drivers.IoTClient/IoTClientPlcDriver.cs:315) 总是返回 wordCount 长度；字节不足时尾部保留 0，也接受最后半字。这抹掉了短帧事实，上层试读的长度防御和采集校验无法区分「设备真的为零」与「未收到」。触发、占位、测量和曲线均可能被错误解码。实际 PLC 库是否会报告成功短帧须以协议故障注入验证，不能据探针声称现场必然发生。

**修复方向：** 对每种协议校验实际载荷字节数，字读不足即抛带地址、请求长度、实收长度的通讯异常，禁止填零当作成功值。

**验收：** loopback 假 PLC 返回截断/半字/空载荷，上层标为读取失败并不落成功结果；完整零值载荷仍正常。

### R10 · P2 · 保留任务按月库名删除，忽略跨月会话里的较新记录

**静态确认。** [RetentionHostedService](D:/code/DataTrace/src/DataTrace.Collector/RetentionHostedService.cs:44) 仅按 monthKey 比较删除；项目会把后站记录存到会话首站所在月份，跨月查询也因此扫描全部保留库。长期 open 会话可以在很旧月库中存入当前记录，仍被整库删除。曲线按实际 TriggerTime 的月份存放，删除会话起始月也不能覆盖跨月关联文件。未检查 active session、待补传及未转运 MES 意图。

**修复方向：** 定义过期单位和跨月会话最长生命周期；删除前检查引用、未完成会话/意图与记录最大时间，协调备份/补传；按关联对象清理大文件并可断点重试。

**验收：** 旧月会话含新月记录、待补传和未转运意图时不误删；完全过期闭合对象可完整清理并留审计。

### R11 · P2 · 写库失败可显示 Idle；健康心跳不能证明在途采集正常

**静态确认。** [工站 fault 判据](D:/code/DataTrace/src/DataTrace.Collector/StationCollectPipeline.cs:109) 未纳入 DatabaseWriteFailed，因此已进入 spool 且回写成功的工站可呈现 Idle。已有补传积压报警，但存在等待阈值，无法替代即时的「缓存待落库」状态。[HealthProbe](D:/code/DataTrace/src/DataTrace.Web/Services/HealthProbe.cs:170) 只根据主循环心跳判 collector；单工站任务卡住时主循环可以继续，healthz 仍 healthy。原始异常消息也可能含路径，与匿名探活不泄露路径的声明不一致。

**修复方向：** 引入持久化/待补传/确认失败等独立状态；监控每个在途任务时限、最后成功采集/持久化、各后台服务心跳；区分宿主 liveness 与业务 readiness；匿名报告使用脱敏错误码。

**验收：** 单工站卡死、月库拒写而 spool 可写、spool 也不可写时，及时出现不同故障状态和关联事件，不只显示「进程活着」。

### R12 · P2 · 全线顺序扫描，单 PLC 初次断链仍影响其他 PLC 节拍

**静态确认；实际影响大小待测。** [扫描循环](D:/code/DataTrace/src/DataTrace.Collector/CollectionHostedService.cs:403) 逐 PLC await，同一 PLC 的点位采集与扫描共用串行队列；首次失败或冷却后重连，连接重试/同步 IoTClient 调用会延迟后续 PLC。冷却机制减少重复代价，但不提供全线隔离。驱动的「Async」接口内部调用同步 Open/Read/Write，取消只能在部分边界生效，试读 10 秒等令牌并不构成硬网络期限保证。

**修复方向：** 每 PLC 独立调度与时限、有限并发/有界队列；扫描与采集请求定义优先级和最大等待；明确第三方同步 IO 超时上界，不能简单超时返回后同时复用仍在执行的连接。

**验收：** 多 PLC 下拔掉一台、制造长曲线和多次试读，其他 PLC 的 P95/P99 采集延迟仍在各自节拍预算内，取消与关闭耗时有界。

### R13 · P2 · 配置审计和版本号不足以重建、比较与回滚完整配置

**静态确认。** [工站保存审计](D:/code/DataTrace/src/DataTrace.Web/Components/Pages/Stations.razor:1394) 仅拼部分字段，TriggerValue、托盘地址/长度、顺序、首末站等关键字段不能完整从这一条还原。ConfigVersion 是失效计数，不是不可变配置版本，CollectRecord 未引用完整配置 revision。另有 [型号保存](D:/code/DataTrace/src/DataTrace.Infrastructure/Persistence/ConfigRepository.Recipes.cs:104) 在外层审计事务提交前修改基线缓存、推送 hub；审计失败回滚数据库不回滚这些内存副作用，可能呈现未提交状态。

**修复方向：** 保存版本化完整配置快照和结构化差异，带操作者、原因、验证结果与兼容版本；采集记录引用配置/算法版本。提交后再发布内存变更事件；回滚是受审计的新版本。

**验收：** 所有关键字段变更可精确比较和还原；模拟审计失败时数据库、运行时 hub 和基线一致；恢复任意历史配置后能重演判定。

### R14 · P2 · 积压与文件输入没有明确资源预算

**静态确认；规模阈值待压测。** [spool ListAsync](D:/code/DataTrace/src/DataTrace.Infrastructure/Storage/FileSpoolStore.cs:54) 一次反序列化全部请求（含曲线），ReplayAll 在处理第一件前已持有整队数据。长期数据库故障恢复可能在最需要恢复时出现内存峰值。[文件读取](D:/code/DataTrace/src/DataTrace.Collector/FileSourceReader.cs:47) 整文件读入且未见大小上限；曲线解压先展开整个文件再校验点数。PLC 请求队列也是无界 channel。深分页跨多个数据库取各自前 Skip+Take 再合并，规模放大后需要单独验收。

**修复方向：** spool 按文件名分页/流式逐条读取；定义文件大小、解压量、队列长度和磁盘积压上限与背压，提前预警。跨库深分页考虑游标或查询索引。

**验收：** 使用至少一天峰值积压量和三年代表性库量，测补传吞吐、内存峰值、查询 P95/P99；超预算输入被清晰拒绝且不影响其他工站。

## 5. L3 验收与量化指标

以下是建议验收方案，不是本轮实测数值。延迟阈值由每条产线的节拍预算决定，不能直接套 100 ms。

| 验收主题 | 建议测试/指标 | 必需结论 |
|---|---|---|
| 故障一致性 | 在读取、提交、索引更新、回写、Outbox relay/send、删 spool 的边界注入硬退出 | 已确认采集无丢失、同事件不重复；未确认事件可定位且恢复决策明确 |
| 长稳 | 72 小时开发验收 + 更长现场试运行，含随机断链/重连 | 无异常退出；句柄、内存趋势稳定；日志/队列/磁盘受预算约束 |
| 延迟 | 各 PLC/工站 P50/P95/P99，排队/读取/判定/落库/回写分别统计 | 健康设备不因另一设备异常而超出节拍预算 |
| 恢复 | 写库拒绝、磁盘不足、spool 损坏、配置库异常、服务重启 | RTO、补传追平时间可测；设备状态、会话和历史数据一致 |
| 数据 | 记录/曲线/归档引用、在制索引、MES 幂等接收、版本引用 | 自动一致性检查零未解释差异；恢复前后可比较 |
| 安全 | 每角色正常操作与越权、撤权/删号/改密后的既有电路、生产 TLS | 敏感动作被即时授权，失败留痕；生产网络前提明确 |
| 用户任务 | 新用户完成配置试读、查询追溯、故障定位与恢复 | 记录操作数、耗时、误操作率；由真实用户试用验证 |
| 交付 | 干净工控机、服务账号、外置 DataRoot、旧库升级与失败回滚 | 原始构建门禁通过；重复演练成功；记录部署/升级/回滚耗时 |
| 回归 | 关键故障矩阵纳入 CI；性能/长稳周期性跑 | 一次故障可由自动化重现并阻止回归；不靠人工记忆 |

恢复承诺必须区分：事务提交的数据、只在内存读到的数据、未回写 PLC 的事件。没有设备事件号/持久化确认协议时，不能承诺断电后所有已读取样本都无损且恰好采一次。涉及实际危险设备动作的部署还需独立安全设计验证，本仓库测试不能证明这一点。

## 6. 实施顺序与产品化决策

1. **先修复业务正确性：** R01/R02/R04/R05/R09；以持久化采集事件、在制更新意图、冻结修订和故障注入构成一次完整验收。
2. **再关闭现场与安全风险：** R03/R06/R07/R08；完成一致备份、动作授权、任务汇合、外置数据真实回滚演练。
3. **补齐运行闭环：** R10/R11/R12/R14；明确服务/设备/任务状态、资源预算、隔离和性能指标。
4. **完成变更治理与交付门禁：** R13、原始构建环境、固定视觉比较环境、持续故障回归、运行时迁移。

截至 2026-10-11，.NET 8 支持将于 **2026-11-10** 结束，应把运行时迁移纳入近期交付计划。使用 .NET 10 SDK 构建 `net8.0` 不等于应用已经迁移到 .NET 10；本机 8.0.29 也不是官方当前列出的 8.0.31。支持期限依据 [微软官方支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)。迁移需同时覆盖 EF/驱动/客户运行时、旧库/恢复/回滚和 UI 回归。

产品决策建议：可以继续做受控试运行；在上述 P1 风险关闭、故障一致性和恢复验收完成前，不应承诺无人值守长期运行、无损断电恢复或成熟商业产品级可靠性。新增功能的优先级应低于这一轮可靠性治理。
